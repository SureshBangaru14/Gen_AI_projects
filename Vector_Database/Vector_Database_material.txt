Vector Database:





What is a Vector Database :

	1. Definition : 

		A Vector Database is a database designed to store, index, and search vectors efficiently.

		Vectors are numerical representations of data such as:

					Text
					Documents
					Images
					Audio
					Videos

		The main purpose of a Vector Database is to find similar data based on meaning or characteristics, rather than only exact keyword matches.

		Simple Definition :

			A Vector Database stores embeddings and finds the most similar embeddings for a given query.
			
			
			
		Example :
		
			Document:
			
				"Python is used for machine learning."

					↓ Embedding Model

				Vector:
				[0.21, -0.45, 0.78, 0.13, ...]
				
				
What is a Vector :

	- A vector is a collection of numerical values.

		Example:

		[0.21, -0.45, 0.78, 0.13]

		- Each number represents one dimension of the vector.

		Vector
		│
		├── Dimension 1 → 0.21
		├── Dimension 2 → -0.45
		├── Dimension 3 → 0.78
		└── Dimension 4 → 0.13

	- Real embedding models usually generate vectors with many more dimensions.

		For example:

			Text
			 ↓
			Embedding Model
			 ↓
			[0.21, -0.45, 0.78, ...]
				     ↑
			       Many dimensions
			       
			       
	Why vectors :

		- Computers can perform mathematical operations on vectors to determine how similar two pieces of data are.
		
		
		
What is an Embedding :

		An embedding is a numerical representation of data that captures useful characteristics or semantic information.

		For text:

			Text
			 ↓
			Embedding Model
			 ↓
			Vector

		Example:

			"How can I learn Python?"
				     ↓
			       Embedding Model
				     ↓
			[0.12, 0.84, -0.31, ...]
			
			
			
Vector Database :

	A Vector Database stores vectors so they can be efficiently searched.

	A stored record can contain:

		ID
		Vector
		Original Text
		Metadata

		Example:

			{
			  "id": "chunk_001",
			  "vector": [0.21, -0.45, 0.78, 0.13],
			  "text": "Employees are eligible for annual leave.",
			  "metadata": {
			    "file": "hr_policy.pdf",
			    "page": 10,
			    "section": "Leave Policy"
			  }
			}

	So conceptually:

		Vector Database
		│
		├── Vector
		├── Text
		├── Metadata
		└── ID
		
		
	Why store metadata :

		Metadata helps identify where the retrieved information came from.

		For example:

			file_name = hr_policy.pdf
			page = 10
			section = Leave Policy

		This is especially useful for RAG applications.
		
		
		
		
How Vector DB Works : 

	The basic process has two parts:

	A. Data Ingestion :
	
		Document
		   ↓
		Chunking
		   ↓
		Embedding Model
		   ↓
		Vectors
		   ↓
		Vector Database

		Example:

			HR Policy PDF
			     ↓
			Chunk 1
			Chunk 2
			Chunk 3
			     ↓
			Embedding Model
			     ↓
			Vector 1
			Vector 2
			Vector 3
			     ↓
			Vector Database
			
			
			
	B. Query :

		When the user asks a question:

			User Query
			    ↓
			Embedding Model
			    ↓
			Query Vector
			    ↓
			Similarity Search
			    ↓
			Most Similar Vectors
			    ↓
			Original Chunks

		Example:

			User:
			"Who is eligible for annual leave?"
				     ↓
			       Query Embedding
				     ↓
				Query Vector
				     ↓
			      Vector DB Search
				     ↓
			       Similar Chunks
				     ↓
			"Employees are eligible for annual
			leave after 12 months..."
			
			
			
			
			
Vector DB Architecture :


			┌─────────────────────────────────────────┐
			│             VECTOR DATABASE             │
			│                                         │
			│  ┌───────────────┐                      │
			│  │    Vectors    │                      │
			│  │               │                      │
			│  │ [0.2,0.4,...] │                      │
			│  │ [0.8,0.1,...] │                      │
			│  └───────┬───────┘                      │
			│          │                              │
			│          ▼                              │
			│  ┌───────────────┐                      │
			│  │ Vector Index  │                      │
			│  └───────┬───────┘                      │
			│          │                              │
			│          ▼                              │
			│  ┌───────────────┐                      │
			│  │   Metadata    │                      │
			│  │               │                      │
			│  │ page          │                      │
			│  │ section       │                      │
			│  │ document      │                      │
			│  └───────────────┘                      │
			│                                         │
			└─────────────────────────────────────────┘
			
			
			The main components are:

				Vector DB
				│
				├── Vector Storage
				├── Vector Index
				├── Metadata
				├── IDs
				└── Similarity Search

				The index is important because searching millions of vectors one-by-one would be inefficient.



			Final Concept : 
			
						 VECTOR DATABASE
							│
					┌───────────────┴───────────────┐
					│                               │
				     STORE                           SEARCH
					│                               │
					▼                                             ▼
				   Embeddings                       Query
					│                               │
					▼                                              ▼
				     Vectors                    Query Embedding
					│                               │
					└───────────────┬───────────────┘
							▼
						 Similarity Search
							│
							▼
						 Relevant Data

				Remember:

					Embedding model creates vectors. Vector Database stores and searches those vectors.
					
					
Why Vector Database  :


		1. Limitations of Traditional Keyword Search : 

			Traditional keyword search looks mainly for exact words or matching terms.

			Example:

			Document:
			"Python is widely used for machine learning."

			Query:
			"Python machine learning"

			Keyword search can find the document because the same keywords exist.

			But consider:

			Document:
			"Python is widely used for machine learning."

			Query:
			"Which programming language is commonly used for ML?"

			The query may not contain the exact words from the document.

			Main limitations :
			
				Traditional Keyword Search
				│
				├── Exact keyword dependency
				├── Synonyms may be missed
				├── Different wording may be missed
				├── Does not understand meaning
				└── Context understanding is limited


		2.Semantic Search :

			Semantic search searches based on the meaning of the query, rather than only matching exact words.

			Example:

				Document:
					"Python is widely used for machine learning."

				Query:
					"Which programming language is commonly used for ML?"

				Even though the wording is different:

					machine learning ≈ ML
					programming language ≈ Python

					an embedding model can represent both texts as vectors.

						Document
						   ↓
						Embedding
						   ↓
						Vector A

						Query
						   ↓
						Embedding
						   ↓
						Vector B

						Vector A ↔ Vector B
						       Similar Meaning
						       
						       
		3. Similarity Search :

			Similarity search finds the vectors that are closest to a query vector.

			Example:

				Query Vector
				     │
				       ▼
				[0.21, 0.45, 0.78, ...]
				     │
				     │
				     ├──────── Vector 1 → Similarity = 0.92
				     ├──────── Vector 2 → Similarity = 0.81
				     ├──────── Vector 3 → Similarity = 0.43
				     └──────── Vector 4 → Similarity = 0.21

				The Vector Database returns the most similar results:

					Top-K
					 │
					 ├── Result 1 → 0.92
					 ├── Result 2 → 0.81
					 └── Result 3 → 0.43

					This is useful when the user wants information that is similar in meaning, not necessarily an exact keyword match.
					
					
		4. RAG Requirement :

			RAG (Retrieval-Augmented Generation) needs a way to retrieve relevant information from a large knowledge base.

			Typical flow:

				Documents
				    ↓
				Chunking
				    ↓
				Embedding
				    ↓
				Vector Database
				    ↓
				      ← User Query
				    ↓
				Query Embedding
				    ↓
				Similarity Search
				    ↓
				Relevant Chunks
				    ↓
				LLM
				    ↓
				Answer

				Without an efficient retrieval mechanism, an LLM cannot simply search through millions of document chunks efficiently.

				Therefore, a Vector Database is commonly used as the retrieval layer in RAG systems.
				
				
				
		5. Recommendation Systems :

			Vector databases can be used to find items that are similar to a user's interests or previous items.

			Example:

				User watches:
				
					"Machine Learning Course"
					       ↓
					Embedding
					       ↓
					User/Item Vector
					       ↓
					Vector Database
					       ↓
					Similarity Search
					       ↓
					Similar Courses

					Results might include:

						1. Deep Learning Course
						2. Python for ML
						3. NLP Course
						4. Generative AI Course

					The same concept can be applied to:

					Products
					Movies
					Music
					Courses
					Articles
					Jobs
					
					
		6. Image Search :

			Images can also be converted into vectors using an embedding model.

			Example:

				Image
				  ↓
				Image Embedding Model
				  ↓
				Image Vector
				  ↓
				Vector Database

				A user can provide another image:

				Query Image
				     ↓
				Embedding
				     ↓
				Query Vector
				     ↓
				Similarity Search
				     ↓
				Similar Images

			Example:

				Query:
				[Image of a red car]

					↓

				Vector Database

					↓

				Similar Images
				├── Red sports car
				├── Red sedan
				└── Red automobile
				
				
				
		7. LLM Applications :

			Vector databases are useful in many LLM-based applications where the model needs access to external information.

			Examples:

				LLM Applications
				│
				├── RAG
				├── Question Answering
				├── Document Search
				├── Enterprise Search
				├── Resume Search
				├── HR Chatbots
				├── Customer Support
				└── Knowledge Assistants

			Example:

				Company Documents
				       ↓
				     Chunks
				       ↓
				   Embeddings
				       ↓
				   Vector DB
				       ↓
				User Question
				       ↓
				Similarity Search
				       ↓
				Relevant Information
				       ↓
				      LLM
				       ↓
				    Answer
				    
				    
				    
				    
				    
Vector Database vs Traditional Database : 



			1. SQL Database :

				A SQL database stores data in structured tables made of rows and columns.

				Example:

				Employees
					┌────┬────────┬────────────┐
					│ ID │ Name   │ Department │
					├────┼────────┼────────────┤
					│ 1  │ Suresh │ AI         │
					│ 2  │ Ravi   │ HR         │
					│ 3  │ John   │ Finance    │
					└────┴────────┴────────────┘

				Example query:

					SELECT *
					FROM Employees
					WHERE Department = 'AI';

				SQL databases are commonly used when data has a defined schema and relationships.

				Examples:

					PostgreSQL
					MySQL
					Oracle
					SQL Server
					
					
					
			2. NoSQL Database :

				A NoSQL database is designed for flexible or non-tabular data models.

				Example document:

					{
					  "name": "Suresh",
					  "skills": [
					    "Python",
					    "RAG",
					    "Vector Database"
					  ],
					  "experience": 5
					}

					The structure can be more flexible than a traditional SQL table.

				Common NoSQL models include:

					Document
					Key-Value
					Column-Family
					Graph

				Examples:

					MongoDB
					Cassandra
					DynamoDB
					Redis
					
					
					
			3. Keyword Search :

				Keyword search primarily looks for words or terms appearing in the data.

				Example:

					Document:
					"Python is used for machine learning."

					Query:
					"Python machine learning"

					The search can match:

					Python
					machine learning

					But:

					Query:
					"Which programming language is commonly used for ML?"

					may be harder for pure keyword search because the wording differs.

					Keyword Search
					      ↓
					Word / Term Matching
					      ↓
					Matching Documents
				
				
				
			4. Semantic Search :

				Semantic search looks for information based on meaning.

				Document:
					"Python is used for machine learning."

				Query:
					"Which programming language is commonly used for ML?"

				The words are different, but the meaning is related.

				The process is:

					Document
					   ↓
					Embedding
					   ↓
					Vector

					Query
					   ↓
					Embedding
					   ↓
					Query Vector

					Query Vector
					     ↓
					Similarity Search
					     ↓
					Similar Meaning

					This is where Vector Databases are particularly useful.
					
					
					
			5. Structured Data :

				Structured data has a predefined format or schema.

					Example:

						Employee Table

						ID | Name   | Age | Department
						---|--------|-----|-----------
						1  | Suresh | 30  | AI
						2  | Ravi   | 28  | HR

						The fields are clearly defined:

							ID
							Name
							Age
							Department

					Examples:

						Employee records
						Orders
						Transactions
						Bank accounts
						Inventory
						Customer records

						Traditional SQL databases are particularly suitable for this type of data.
						
						
			6. Unstructured Data :

				Unstructured data does not naturally follow a fixed table structure.

				Examples:

					PDF
					Text
					Images
					Audio
					Videos
					Emails
					Documents
					Resumes

				For example:

					HR Policy.pdf
					      ↓
					"This company provides employees
					with 20 days of annual leave..."

					The information does not naturally fit into:

					ID | Name | Age | Department

				For AI applications, this information can be:

					Document
					   ↓
					Chunks
					   ↓
					Embeddings
					   ↓
					Vectors
					   ↓
					Vector Database
					
					
			7. Query Differences :
			
				Traditional SQL Query :
				
					SELECT *
					FROM employees
					WHERE department = 'AI';

					The database evaluates the specified structured conditions.

					SQL Query
					   ↓
					Structured Conditions
					   ↓
					Matching Rows
					
				Keyword Search :
				
					Query:
					"Python developer"
					       ↓
					Keyword Matching
					       ↓
					Documents containing relevant terms
					
					
					
				Vector Search :
				
					Query:
					
						"Developer experienced in Python"
						       ↓
						Embedding Model
						       ↓
						Query Vector
						       ↓
						Vector Database
						       ↓
						Similarity Search
						       ↓
						Most Similar Chunks
						
						
						
						
			Quick Comparison :
			
				┌────────────────────┬──────────────────────┐
				│ Technology         │ Main Purpose         │
				├────────────────────┼──────────────────────┤
				│ SQL Database       │ Structured data      │
				│ NoSQL Database     │ Flexible data        │
				│ Keyword Search     │ Word matching        │
				│ Vector Database    │ Similarity search    │
				└────────────────────┴──────────────────────┘
				
				
				
Vector Store vs Vector Database :

		1. Vector Store : 

			A Vector Store is a storage system or abstraction used to store embeddings and perform similarity searches.

			It is commonly used in AI/RAG applications.

				Basic flow:

				Document
				   ↓
				Chunking
				   ↓
				Embedding Model
				   ↓
				Vector
				   ↓
				Vector Store
				   ↓
				Similarity Search

				A Vector Store generally provides operations such as:

					Add vectors
					Search vectors
					Delete vectors
					Retrieve documents
					Store metadata
					
					
		2. Vector Database :

			A Vector Database is a database system specifically designed to store, index, manage, and search large collections of vectors.

			Basic architecture:

					 Vector Database
					       │
				┌──────────────┼──────────────┐
				↓                    ↓                   ↓
			     Vectors        Metadata        Index
				│              │              │
				└──────────────┼──────────────┘
					          ↓
					Similarity Search

			It is designed for applications where vector search is an important part of the production system.

			Examples:

				Chroma
				Qdrant
				Milvus
				Weaviate
				Pinecone
				
				
		3. Similarities :

			Both Vector Stores and Vector Databases can be used to:

				Store embeddings
				      ↓
				Store metadata
				      ↓
				Perform similarity search
				      ↓
				Retrieve relevant documents/chunks

				Both are commonly used in:

					RAG
					Semantic Search
					Document Search
					Recommendation Systems
					AI Applications

					Example:

						User Query
						    ↓
						Query Embedding
						    ↓
						Vector Search
						    ↓
						Similar Vectors
						    ↓
						Relevant Documents
						
						
		4. Differences :

			The terms are sometimes used interchangeably, but they can refer to different levels of abstraction.

			Vector Store
			
				Application
				    ↓
				Vector Store
				    ↓
				Vector Storage / Search

				It often focuses on providing a convenient interface for an application or framework.

			Vector Database
			
				Application
				    ↓
				Vector Database
				    ↓
				Storage
				Indexing
				Metadata
				Filtering
				Search
				Persistence
				Scalability
				
				
			A Vector Database is a more complete database system.

			Simple difference :

				Vector Store = vector storage/retrieval abstraction

				Vector Database = database system built to manage vector data at scale
				
				
		5. Persistence :
		
			Vector Store

				Persistence depends on the implementation.

				Some vector stores may be:

					In-memory
					Local
					File-based
					Database-backed
					Cloud-backed

					Example:

						Application starts
						      ↓
						Vectors loaded
						      ↓
						Application stops
						      ↓
						Data may be lost

				if the underlying store is only in memory.
				
				
			Vector Database : 

				A Vector Database is designed for persistent data storage.

					Documents
					   ↓
					Embeddings
					   ↓
					Vector Database
					   ↓
					Persistent Storage

					After restarting the application:

						Application Restart
						       ↓
						Connect to Vector DB
						       ↓
						Existing vectors available

						Persistence is therefore an important consideration for production systems.
						
		6. Scalability :
		
				Vector Store :

					A simple Vector Store may be suitable for:

						Small datasets
						Development
						Experiments
						Proof of Concepts
						Local RAG applications

						Example:

							1,000 chunks
							      ↓
							Local Vector Store
							
				Vector Database :

					A Vector Database is designed for larger workloads and production requirements.

						Millions of vectors
						       ↓
						Vector Database
						       ↓
						Indexing
						       ↓
						Fast Similarity Search

					Production systems may require:

						Large-scale storage
						Fast indexing
						Concurrent queries
						Metadata filtering
						High availability
						Horizontal scaling
						Monitoring
						
						
		7. Production Usage :
		
				Development / Learning

				A Vector Store can be sufficient:

					PDF
					 ↓
					Chunking
					 ↓
					Embedding
					 ↓
					Vector Store
					 ↓
					Search

					Good for:

						Learning
						Testing
						POC
						Small RAG applications
						
						
						
				Production :

					A production application generally needs a robust persistent backend:

						Documents
						    ↓
						Chunking
						    ↓
						Embedding
						    ↓
						Vector Database
						    ↓
						Index
						    ↓
						Similarity Search
						    ↓
						Metadata Filtering
						    ↓
						Retrieved Chunks
						    ↓
						  LLM
						  

Embeddings → Vector DB :

			1. Document :

				A document is the original source of information that we want to store and search.

				Examples:

					PDF
					DOCX
					Web page
					Resume
					HR Policy
					BOL
					Invoice

				Example:

					HR_Policy.pdf
					Employees are eligible for annual leave
					after completing 12 months of service.

				Flow:

					Document
					   ↓
					Text Extraction
					   ↓
					Document Text					  
						  
						  
			2. Chunk :

					A document is usually divided into smaller pieces called chunks before creating embeddings.

					Example:

						Document
						   ↓
						Chunking
						   ↓
						Chunk 1
						Chunk 2
						Chunk 3

					Example:

						Chunk 1:
						Employees are eligible for annual leave
						after completing 12 months of service.

						Chunk 2:
						Employees must submit leave requests
						through the HR portal.

					Why?

						Because embedding an entire large document as one vector can make retrieval less precise.
						
						
			3. Embedding Model :

					An embedding model converts text into a numerical vector.

						Chunk
						  ↓
						Embedding Model
						  ↓
						Vector

					Example:

						Chunk:
						"Employees are eligible for annual leave."

							  ↓

						Embedding Model

							  ↓

						[0.21, -0.45, 0.78, 0.13, ...]

					Examples of embedding models include:

						Sentence Transformers
						OpenAI Embeddings
						Qwen Embedding Models
						
						
			4. Vector Generation :

					The embedding model generates a vector for each chunk.

					Example:

						Chunk 1
						   ↓
						[0.21, -0.45, 0.78, 0.13]

						Chunk 2
						   ↓
						[0.18, -0.41, 0.74, 0.20]

						Chunk 3
						   ↓
						[0.81, 0.12, -0.32, 0.55]

						So:

						Multiple Chunks
						      ↓
						Embedding Model
						      ↓
						Multiple Vectors

			5. Vector Dimensions :

					Vector dimensions means the number of numerical values in one vector.

					Example:

						[0.21, -0.45, 0.78, 0.13]

						This vector has:

							4 dimensions

						A real embedding model might produce:

							384 dimensions
							768 dimensions
							1024 dimensions
							1536 dimensions
							
							
						For example:

							Chunk
							  ↓
							Embedding Model
							  ↓
							[0.21, -0.45, 0.78, ...]
								↑
							   384 numbers
							   
							   
					The vector database must store vectors with the dimension expected by the embedding model.
					
					
					
			6. Store Vector :

				After generating the vector, store it in the Vector DB.

				Example:

					Chunk
					   ↓
					Embedding
					   ↓
					Vector
					   ↓
					Vector DB

				Example record:

					{
					  "id": "chunk_001",
					  "vector": [0.21, -0.45, 0.78, 0.13]
					}
					
					
					
			7. Store Metadata :

				Metadata provides additional information about the vector.

				Example:

					{
					  "metadata": {
					    "file_name": "hr_policy.pdf",
					    "page_number": 10,
					    "section": "Leave Policy"
					  }
					}

				Metadata can be used for:

					Filtering
					Source identification
					Page identification
					Document identification
					Access control

				For your BOL project, metadata could be:

					{
					  "bol_number": "73202660",
					  "page_number": 2,
					  "chunk_type": "Details",
					  "file_name": "bol.pdf"
					}
					
					
			8. Store Document ID :

				Each stored chunk should have a unique document/chunk ID.

				Example:

					document_id = "bol_73202660"

					or:

					chunk_id = "bol_73202660_detail_001"

				Example complete record:

					{
					  "id": "bol_73202660_detail_001",
					  "vector": [0.21, -0.45, 0.78, 0.13],
					  "metadata": {
					    "document_id": "bol_73202660",
					    "file_name": "bol.pdf",
					    "page_number": 2,
					    "chunk_type": "Details"
					  },
					  "text": "10 cartons, 500 LB, freight class 70"
					}
					
					
			Complete Flow :
			
			
					Document
					   ↓
					Chunk
					   ↓
					Embedding Model
					   ↓
					Vector Generation
					   ↓
					Vector Dimensions
					   ↓
					Store Vector
					   ↓
					Store Metadata
					   ↓
					Store Document ID
					   ↓
					Vector Database
					
			
					Ex One record :
					
						Vector DB Record
						│
						├── Document ID
						├── Vector
						├── Text / Chunk
						└── Metadata
						      │
						      ├── File Name
						      ├── Page Number
						      ├── Section

06. Collections / Indexes :


			1. Collection :

				A collection is a logical container used to store related vectors, documents, and metadata.

				Think of it like a table or group for vector data.

				Example:

					Vector Database
					│
					├── hr_documents
					├── resumes
					├── bol_documents
					└── invoices

					For example, a bol_documents collection can contain:

						BOL Chunk 1 → Vector + Metadata
						BOL Chunk 2 → Vector + Metadata
						BOL Chunk 3 → Vector + Metadata
						
						
			2. Collection Naming :

				Collection names should clearly describe the data stored inside them.

				Good names:

					hr_documents
					resume_embeddings
					bol_documents
					invoice_chunks
					legal_documents

				Avoid unclear names:

					test
					data1
					collection123
					abc

				For production, use a consistent naming convention:

					<domain>_<document_type>

					Example:

						hr_policies
						financial_documents
						bol_documents
						technical_documents
						
						
			3. Vector Index :

				A vector index is a data structure used to make vector similarity search faster.

				Without an efficient index:

					Query Vector
					     ↓
					Compare with Vector 1
					Compare with Vector 2
					Compare with Vector 3
					...
					Compare with Vector 1,000,000

					This can be expensive.

					With an index:

						Query Vector
						     ↓
						Vector Index
						     ↓
						Find likely nearest vectors
						     ↓
						Top-K Results

					Common vector indexing approaches include:

						HNSW
						IVF
						PQ
						
						
					Ex :
					
					
						HNSW — Example

							Suppose we have 4 document chunks:

								Chunk 1 → "Employees are eligible for annual leave."
								Chunk 2 → "Employees must follow attendance policy."
								Chunk 3 → "Annual leave can be carried forward."
								Chunk 4 → "Company provides health insurance."

							First, the embedding model converts them into vectors:

								Chunk 1 → [0.12, 0.45, 0.78, ...]
								Chunk 2 → [0.32, 0.11, 0.56, ...]
								Chunk 3 → [0.15, 0.48, 0.81, ...]
								Chunk 4 → [0.90, 0.21, 0.10, ...]

							HNSW creates an index over these vectors:

									    HNSW INDEX
										│
								      ┌─────────┴─────────┐
								      │                   │
								   Chunk 1              Chunk 4
								      │
								      ├───────────────┐
								      │               │
								   Chunk 3          Chunk 2

							Now the user asks:

								Query:
								
									"Can I take annual leave?"
								
								
								The query is converted into a vector:

									Query
									  ↓
									[0.14, 0.46, 0.79, ...]

									HNSW searches the index:

									Query Vector
									     │
									       ↓
									 HNSW Index
									     │
									     ├── Chunk 1
									     ├── Chunk 3
									     ├── Chunk 2
									     └── Chunk 4

									With L2 distance, you might get results conceptually like:

									RESULTS

										Rank    Chunk       Distance
										--------------------------------
										1       Chunk 1      0.08
										2       Chunk 3      0.15
										3       Chunk 2      0.62
										4       Chunk 4      1.21
						
						
			4. Index Creation :

				When vectors are added to a vector database, an index can be created or maintained to support efficient similarity search.

				Basic concept:

					Documents
					    ↓
					Chunks
					    ↓
					Embeddings
					    ↓
					Vectors
					    ↓
					Collection
					    ↓
					Vector Index
					    ↓
					Similarity Search

				Example:

					bol_documents
					      │
					      ├── Vector 1
					      ├── Vector 2
					      ├── Vector 3
					      ├── Vector 4
					      └── Vector 5
						      ↓
						 Vector Index

					The exact index-creation process depends on the Vector Database being used.
					
					
					
			5. Index Configuration :

				Index configuration controls how the vector search behaves.

				Important settings can include:

					Distance metric
					Index type
					Search parameters
					Construction parameters
					Vector dimensions
					
				Distance Metric :

					Common choices:

						Cosine similarity
						Euclidean distance
						Dot product

				Example:

					Embedding Model
					      ↓
					768-dimensional vectors
					      ↓
					Vector Index
					      ↓
					Cosine similarity
					
				The configuration should be compatible with the embedding model and the application's retrieval requirements.


			6. Collection vs Index :
			
				Collection :

					A collection organizes and stores the vector records.

					Collection
					│
					├── Vector
					├── Text
					├── Metadata
					└── ID

				Index :

					An index helps search those vectors efficiently.

					Index
					   ↓
					Efficient Vector Search
					Simple Difference
					Collection
					    ↓
					WHERE the vector data is stored

					Index
					    ↓
					HOW the vector data is searched efficiently
					
					
					
				Example :
				
					Vector Database
					│
					└── bol_documents          ← Collection
					      │
					      ├── BOL Vector 1
					      ├── BOL Vector 2
					      ├── BOL Vector 3
					      └── BOL Vector 4
						     │
						       ▼
						Vector Index        ← Search structure
						     │
						       ▼
					       Similarity Search
					       
					Remember :

						Collection = container for related vector records.

						Index = structure that makes searching those vectors efficient.

		1. What is Metadata :

				Metadata = information about the document or chunk.

				The actual content is:

				"Employees are eligible for annual leave."

				Metadata describes that content:

					{
					    "file_name": "hr_policy.pdf",
					    "page_number": 10,
					    "document_type": "HR Policy"
					}

				Think:

					Document
					   │
					   ├── Text       → Actual content
					   ├── Vector     → Numerical representation
					   └── Metadata   → Information about the content

			A metadata field is a key-value pair.

				metadata = {
				    "file_name": "hr_policy.pdf",
				    "page_number": 10,
				    "document_type": "HR Policy",
				    "tenant_id": "company_001"
				}

				Here:

					file_name      → field
					hr_policy.pdf  → value

					page_number    → field
					10             → value

				Search only within documents that satisfy a condition.

				Example:

					results = collection.query(
					    query_texts=["annual leave policy"],
					    n_results=5,
					    where={
						"document_type": "HR Policy"

					Conceptually:

						All Documents
						      ↓
						Metadata Filter
						      ↓
						HR Policy documents
						      ↓
						Semantic Search
						      ↓
						Top 5 results

				metadata = {

				    "document_version": 2.0             # number

				Common types:

					String
					Integer
					Float
					Boolean

						"tenant_id": "company_A"
					    }

Distance / Similarity :


			This topic explains how ChromaDB decides which vectors are close to the query vector.
			
	
			1. Similarity :

				Similarity tells us how similar two vectors are.

				Example:

					Query
					"annual leave policy"
					       ↓
					    Vector A

					Document
					"Employees can take annual leave..."
					       ↓
					    Vector B

					Vector A ↔ Vector B
					       ↓
					   Similarity

				Higher similarity generally means:

					More similar
					     ↓
					More relevant
								

			2. Distance :

				Distance tells us how far two vectors are from each other.

				Query Vector
				     ●
				      \
				       \
					● Document Vector

				Smaller distance means:

					Closer
					  ↓
					More similar

					So:

					Similarity → Higher is usually better

					Distance   → Lower is usually better
					
			
			3. Similarity Score :

				A similarity score is a numerical value representing how similar two vectors are.

				Example:

					Query: "annual leave"

					Chunk 1 → 0.91
					Chunk 2 → 0.76
					Chunk 3 → 0.42

				Ranking:

					Chunk 1 → 0.91  ← Best
					Chunk 2 → 0.76
					Chunk 3 → 0.42
					
			4. Distance Score :

				A distance score represents how far vectors are from each other.

				Example:

					Chunk 1 → 0.12
					Chunk 2 → 0.35
					Chunk 3 → 0.81

				Ranking:

					Chunk 1 → 0.12  ← Best
					Chunk 2 → 0.35
					Chunk 3 → 0.81

				Because:

					Lower distance = closer = more relevant

					Important for ChromaDB: the distances returned by collection.query() are distance values according to the collection's configured metric. 
					Don't automatically interpret them as a percentage or as "similarity score."
					
					
					
			5. Cosine :

				Cosine measures the angle/direction between vectors.

				For text embeddings, cosine is commonly used.

				Concept:

					Vector A ─────────→
					Vector B ────────→

					Small angle
					    ↓
					More similar

				ChromaDB:

					collection = client.get_or_create_collection(
					    name="hr_documents",
					    configuration={
						"hnsw": {
						    "space": "cosine"
						}
					    }
					)
					
					
				Concept:

					HNSW
					 ↓
					Index
					 ↓
					Cosine distance
					 ↓
					Vector search
					
					
			6. Euclidean :

				Euclidean distance = L2 distance.

				It measures the straight-line distance between vectors.

				Vector A ●────────────● Vector B
					     distance

				ChromaDB:

					collection = client.get_or_create_collection(
					    name="hr_documents",
					    configuration={
						"hnsw": {
						    "space": "l2"
						}
					    }
					)

				Here:

					"hnsw" → Indexing algorithm
					"l2"   → Euclidean distance
					
					
					
			7. Dot Product :

				Dot product compares vectors based on their components and magnitudes.

				Example:

					A = [1, 2]
					B = [3, 4]

					A · B
					= (1 × 3) + (2 × 4)
					= 11

				In ChromaDB:

					collection = client.get_or_create_collection(
					    name="hr_documents",
					    configuration={
						"hnsw": {
						    "space": "ip"
						}
					    }
					)

				Here:

					"ip" → Inner Product
					
					
					
Cosine Similarity :

			1. Definition :

				Cosine Similarity measures how similar two vectors are by measuring the angle between them.

				In RAG:

					User Query
					    ↓
					Embedding Model	
					    ↓
					Query Vector
					    ↓
					Compare with document vectors
					    ↓
					Cosine Similarity
					    ↓
					Most similar chunks

					The important idea:

						Smaller angle → more similar meaning.
						
						
			2. Formula :

					The formula is:

								       A · B
						Cosine Similarity = ─────────────
								    ||A|| ||B||

					Where:

						A · B

							= dot product of vectors A and B

						||A||

							= magnitude/length of vector A

						||B||

							= magnitude/length of vector B

						Simple example
							A = [1, 0]
							B = [1, 0]

						They point in exactly the same direction:

							Cosine Similarity = 1
							
							
			3. Range :

					For general vectors, cosine similarity ranges from:

						-1  ─────────  0  ─────────  +1
						│              │              │
						Opposite      Unrelated      Same
						direction                    direction

					For many modern text-embedding models, practical values may often be concentrated in a narrower positive range, 
					so don't assume that 0.8 always means exactly 80% similarity.
					
					
					
			4. Meaning of Score :

					Conceptually:

						Score
						  ↓
						1.00
						 │
						 ├── Very similar direction
						 │
						0.80
						 │
						 ├── Strong similarity
						 │
						0.50
						 │
						 ├── Some similarity
						 │
						0.00
						 │
						 └── Little/no directional similarity

					For example:

						Query:
						"How many vacation days can an employee take?"

						Chunk A:
						"Employees are entitled to annual leave."

						Similarity → 0.89

						Chunk B:
						"The company provides health insurance."

						Similarity → 0.21
						
						
			5. Normalized Vectors :

					A normalized vector has a magnitude of 1.

						Original Vector
						      ↓
						Normalization
						      ↓
						Unit Vector

					Formula:

						A_normalized = A / ||A||

						Example:

							A = [3, 4]

							Magnitude:

							√(3² + 4²)
							= 5

					Normalized:

						A = [3/5, 4/5]

						A = [0.6, 0.8]

						Magnitude:

							√(0.6² + 0.8²) = 1
							
							
			HNSW = Indexing algorithm and now:

					Cosine = Distance/similarity space

					So a ChromaDB collection can conceptually be:

						collection = client.get_or_create_collection(
						    name="hr_documents",
						    configuration={
							"hnsw": {
							    "space": "cosine"
							}
						    }
						)

					Meaning:

						Collection
						   │
						   ├── HNSW
						   │    └── Indexing algorithm
						   │
						   └── Cosine
							└── Vector distance/similarity space

					Remember:

						Cosine Similarity
						       ↓
						Measures direction/angle between vectors
						       ↓
						Higher similarity → generally more similar
						       ↓
						Useful for semantic text retrieval
						
						
						
Euclidean Distance :

		1. Definition :

			Euclidean Distance measures the straight-line distance between two vectors.

			In vector databases:

				Query Vector
				     │
				     │
				     │ distance
				     │
				       ▼
				Document Vector

			The basic idea is:

				Smaller distance → vectors are closer → generally more similar.
				
				
				
		2. Formula :

				For two vectors:

					A = [a₁, a₂, ..., aₙ]

					B = [b₁, b₂, ..., bₙ]

				Euclidean distance is:

						      ┌───────────────────────────────
					Distance =    √ (a₁-b₁)² + (a₂-b₂)² + ... + (aₙ-bₙ)²
						      ───────────────────────────────
				Simple example :
				
					A = [1, 2]

					B = [4, 6]

				Calculate:

					Distance
					= √((1-4)² + (2-6)²)

					= √(9 + 16)

					= √25

					= 5

				So:

					Euclidean Distance = 5
					
					
					
		3. Distance Interpretation :

				Unlike cosine similarity:

					Cosine Similarity
						→ Higher generally means more similar

					Euclidean Distance
						→ Lower generally means more similar

				Example:

					Query → Document A = 0.20
					Query → Document B = 0.70
					Query → Document C = 1.50

				Ranking:

					1. Document A → 0.20  ← Closest
					2. Document B → 0.70
					3. Document C → 1.50  ← Farthest
					
					
		4. Low Distance :

				Low Euclidean distance means the vectors are close together.

					Vector A ●────● Vector B
						  ↑
					       Small distance

				Example:

					Query
					"annual leave policy"

					Chunk 1
					"Employees can take annual leave."

					Distance = 0.15

					A low distance indicates that the vectors are close in the embedding space.
					
					
					
		5. High Distance :

				High Euclidean distance means the vectors are farther apart.

					Vector A ●────────────────────● Vector B
							 ↑
						    Large distance

				Example:

					Query
					"annual leave policy"

					Chunk 2
					"Company cafeteria timings."

					Distance = 1.80

					Generally:

						Low distance
						     ↓
						Closer vectors
						     ↓
						More relevant


						High distance
						     ↓
						Farther vectors
						     ↓
						Less relevant
						
						
		6. Use Cases :

				Euclidean distance can be useful when the geometry and magnitude of the embedding vectors are meaningful.

				Common applications include:

					Euclidean Distance
					│
					├── Vector similarity search
					│
					├── Clustering
					│
					├── Recommendation systems
					│
					├── Image feature comparison
					│
					├── Anomaly detection
					│
					└── Machine-learning feature spaces

					For text RAG, the best metric depends on the embedding model and how its vectors are trained/normalized. 
					Don't choose L2 merely because it is mathematically simple.
					
					
		ChromaDB Example :

				You learned earlier:

					HNSW
					 ↓
					Indexing algorithm

					L2
					 ↓
					Euclidean distance

					So:

						collection = client.get_or_create_collection(
						    name="hr_documents",
						    configuration={
							"hnsw": {
							    "space": "l2"
							}
						    }
						)

				This means:

					ChromaDB Collection
					       │
					       └── hr_documents
						      │
						      └── HNSW
							   │
							   └── L2
								│
								└── Euclidean Distance
								
								

Dot Product :

		1. Definition :

			Dot Product is an operation between two vectors that produces a single number (scalar).

			For vector search, the dot product can be used to measure how strongly two vectors align.

			Query Vector
			      ↓
			   Dot Product
			      ↓
			Document Vector
			      ↓
			   Score
			   
			   
		2. Formula :

				For two vectors:

					A = [a₁, a₂, a₃]

					B = [b₁, b₂, b₃]

				The dot product is:

					A · B
					= (a₁ × b₁)
					+ (a₂ × b₂)
					+ (a₃ × b₃)
					
					Example :
					
						A = [1, 2, 3]

						B = [4, 5, 6]

				Then:

					A · B
					= (1×4) + (2×5) + (3×6)

					= 4 + 10 + 18

					= 32

				Therefore:

					Dot Product = 32
				
				
		3. Vector Magnitude :

					Magnitude means the length of a vector.

					For:

						A = [3, 4]

						Magnitude is:

							|A| = √(3² + 4²)

							    = √25

							    = 5

					So:

						A = [3,4]

						Magnitude = 5

						The dot product can be expressed as:

						A · B = |A| |B| cos(θ)

						This shows that dot product depends on both:

							Magnitude
							     +
							Direction
							
							
							
		4. Vector Direction :

					The angle between two vectors affects their dot product.

					Same direction:

							A ─────────→
							B ─────────→

					Dot product → Positive / large

					Opposite direction:

							A ─────────→

							B ←─────────

					Dot product → Negative

						Perpendicular:

							B
							↑
							│
							│
							└────────→ A

						Dot product → 0
						
						
						
		5. Normalized Vectors :

					A normalized vector has magnitude 1.

					Example:

						A = [3, 4]

					Magnitude:

						|A| = 5

					Normalize:

						A_normalized
						= [3/5, 4/5]

						= [0.6, 0.8]

					Now:

						√(0.6² + 0.8²)
						= 1

					When both vectors are normalized:

						A · B

						is equal to their cosine similarity.

					Because:

						A · B
						────────────
						|A| |B|
						
						
					and if:

						|A| = 1
						|B| = 1

						then:

							Cosine Similarity = A · B

							This is an important relationship:

								Normalized vectors
									↓
								   Dot Product
									↓
								Same value as cosine similarity
								
								
								
			6. Use Cases :

						Dot product is used in:

							Dot Product
							│
							├── Vector Search
							│
							├── Recommendation Systems
							│
							├── Semantic Search
							│
							├── Information Retrieval
							│
							├── Machine Learning
							│
							├── Neural Networks
							│
							└── Ranking Systems

							For vector databases, Inner Product (IP) is commonly associated with dot-product-based retrieval.

							In ChromaDB:

								collection = client.get_or_create_collection(
								    name="hr_documents",
								    configuration={
									"hnsw": {
									    "space": "ip"
									}
								    }
								)
								
								
								
							Here:

								"hnsw"
								   ↓
								Indexing algorithm

								"ip"
								   ↓
								Inner Product
								   ↓
								Dot-product-based distance space
								
								
							HNSW
							  ↓
							Indexing algorithm

							Cosine / L2 / IP
							  ↓
							Distance/search space
							
							
							
							
Top-K Search :

			1. What is Top-K?

				Top-K means retrieving the K most relevant results for a query.

				Example:

					User Query
					    ↓
					Vector Search
					    ↓
					100 matching chunks
					    ↓
					Rank by similarity/distance
					    ↓
					Select Top-K
					
					
					
				If:

					n_results=5

					then:

						Top-K
						  ↓
						K = 5
						  ↓
						Return 5 results
						
						
						
						
Metadata Filtering :


		Metadata filtering means restricting vector search to records whose metadata satisfies specified conditions.
		
		1. Exact Match :

					Exact match checks whether a metadata field equals a particular value.

					Suppose the stored metadata is:

						metadata = {
						    "document_type": "BOL",
						    "tenant_id": "customer_001",
						    "page_number": 2
						}

					Search only BOL documents:

						results = collection.query(
						    query_texts=["shipment information"],
						    n_results=5,
						    where={
							"document_type": "BOL"
						    }
						)

					Meaning:

						document_type == "BOL"
						
						
		2. Numeric Filtering :

				Numeric filtering is used for numbers such as:

					page_number
					year
					version
					weight

					Example:

						results = collection.query(
						    query_texts=["shipment information"],
						    n_results=5,
						    where={
							"page_number": {
							    "$gte": 2
							}
						    }
						)

				Meaning:

					page_number >= 2

				Common numeric operators:

					$gt   → greater than
					$gte  → greater than or equal
					$lt   → less than
					$lte  → less than or equal
					$eq   → equal
					$ne   → not equal
					
					
		3. Date Filtering :

				Dates can be stored as metadata values and filtered according to the supported metadata value/operator types.

				Example metadata:

					metadata = {
					    "created_date": "2026-09-04"
					}

				For date-range filtering, a common approach is to store a comparable date representation and use numeric/range operators.

				For example, store:

					metadata = {
					    "created_date": 20260904
					}

				Then:

					results = collection.query(
					    query_texts=["BOL shipment"],
					    n_results=5,
					    where={
						"created_date": {
						    "$gte": 20260901
						}
					    }
					)
					
					
		4. AND Conditions :

					AND means all conditions must be satisfied.

					Example:

						where={
						    "$and": [
							{
							    "tenant_id": "customer_001"
							},
							{
							    "document_type": "BOL"
							}
						    ]
						}

					Meaning:

						tenant_id = customer_001
							AND
						document_type = BOL

					Conceptually:

						All Documents
						      ↓
						tenant_id = customer_001
						      ↓
						document_type = BOL
						      ↓
						Allowed records
						
						
						
		5. OR Conditions :

					OR means at least one condition must be satisfied.

					Example:

						where={
						    "$or": [
							{
							    "document_type": "BOL"
							},
							{
							    "document_type": "Invoice"
							}
						    ]
						}

					Meaning:

						document_type = BOL
							OR
						document_type = Invoice

					Result:

						BOL       ✓
						Invoice   ✓
						Resume    ✗
						PO        ✗
						
						
						
Indexing Algorithms :


			1. HNSW :
			
					HNSW = Hierarchical Navigable Small World

						HNSW is a graph-based indexing algorithm used for fast approximate nearest-neighbor search.

					Basic concept :

						Instead of comparing the query with every vector:

							Query
							  ↓
							Compare with ALL vectors
							  ↓
							Find nearest

					HNSW creates connections between vectors:

							 Layer 2
							   ●
							  / \
							 /   \
							●     ●
							 \   /
							  \ /
							   ●

							 Layer 1
						  ●────●────●────●
						   \   │   / \   /
						    \  │  /   \ /
						     ●─●───────●

							 Layer 0
					      ●──●──●──●──●──●──●──●
					      
					      
					      
					     During search:

								Query
								  ↓
								Start at upper layer
								  ↓
								Move toward closer vectors
								  ↓
								Go to lower layer
								  ↓
								Find nearest vectors
								  ↓
								Top-K
								
								Why HNSW?
									HNSW
									 ↓
									Graph
									 ↓
									Fewer vectors need to be examined
									 ↓
									Fast search
									 ↓
									Good recall
									
									Remember :
									
										HNSW = Graph-based ANN index
										
										
										
			2. IVF :
			
			
						IVF = Inverted File Index

						IVF divides vectors into clusters.

						Suppose:

						1,000,000 vectors

						Instead of searching all vectors:

							1,000,000
							      ↓
							     IVF
							      ↓
							Clusters

							For example:

								     IVF
								      │
							      ┌───────┼────────┐
							        ↓          ↓           ↓
							   Cluster  Cluster  Cluster
							      1        2        3
							      │        │        │
							   vectors  vectors  vectors
							   
							 
						  Why IVF?

							Because you don't need to search every vector.

							Without IVF:

								Query
								 ↓
								1,000,000 vectors


							With IVF:

								Query
								 ↓
								Find relevant cluster
								 ↓
								Search smaller set
								
								
							Remember :
							
								IVF = Cluster-based indexing
								
								
								
			3. IVF Flat :

					IVF Flat combines:

							IVF
							 +
							Flat

					Here:

						IVF → divides vectors into clusters.
						Flat → keeps the original vectors without PQ compression.
						
						
					Structure :
					
						Vectors
						   ↓
						IVF
						   ↓
						Clusters
						   │
						   ├── Cluster 1
						   │      ├── Original Vector
						   │      ├── Original Vector
						   │      └── Original Vector
						   │
						   ├── Cluster 2
						   │      ├── Original Vector
						   │      └── Original Vector
						   │
						   └── Cluster 3
						   
						   
					Remember :
					
							IVF Flat = IVF + original/uncompressed vectors
							
							
							
			4. IVF PQ :

					IVF PQ combines two ideas:

								IVF
								 +
								PQ
								
					IVF :

						Reduces the search area.

							All vectors
							    ↓
							Clusters
							    ↓
							Relevant clusters
						
					PQ :

						Reduces the vector representation/storage.

						Vector
						   ↓
						Split into sub-vectors
						   ↓
						Quantize
						   ↓
						Compressed representation
						
						
					Together:

							  IVF PQ
							    │
						  ┌─────────┴─────────┐
						  ↓                            ↓
						 IVF                  PQ
						  ↓                            ↓
					     Find clusters       Compress vectors
						  ↓                            ↓
					     Smaller search       Less memory
						  └─────────┬─────────┘
							      ↓
							  Search
							     ↓
							  Top-K
							  
					Important :
					
						IVF PQ
						│
						├── IVF → reduces search area
						└── PQ  → compresses vectors
						
					Remember :
					
						IVF PQ = IVF + Product Quantization
						
						
						
			One-line memory trick :
			
					HNSW
					→ Graph

					IVF
					→ Clusters

					IVF Flat
					→ Clusters + Original Vectors

					IVF PQ
					→ Clusters + Compressed Vectors

					PQ
					→ Compress vectors by sub-vector quantization (float32 to float16) type example

					Vector Compression
					→ General technique for reducing vector storage
