# 1. RAG FUNDAMENTALS

		RAG = Retrieval-Augmented Generation

		RAG combines:
		
			1. Information Retrieval
			2. Large Language Model (LLM)

		Basic idea:

			User Question
			      ↓
			Retrieve Relevant Information
			      ↓
			Provide Retrieved Information to LLM
			      ↓
			Generate Answer


==================================================
1. WHAT IS RAG?
==================================================

		RAG stands for Retrieval-Augmented Generation.

		RAG is an architecture where an LLM retrieves relevant information from an external knowledge source and uses that information as context to generate an answer.

		Simple flow:

			User Question
			      ↓
			Retriever
			      ↓
			Knowledge Base
			      ↓
			Relevant Information
			      ↓
			   LLM
			      ↓
			Final Answer


		Example:

			Suppose a company has:

			    HR_Policy.pdf
			    Leave_Policy.pdf
			    Salary_Policy.pdf

		User asks:

		    "How many sick leaves can an employee take?"

		The LLM may not know the company's internal leave policy.

		RAG retrieves the relevant section from Leave_Policy.pdf and provides it to the LLM.

		Flow:

			Question
			   ↓
			Search Knowledge Base
			   ↓
			Leave_Policy.pdf
			   ↓
			Relevant Chunk
			   ↓
			 LLM
			   ↓
			Answer


		Therefore:

			RAG = Retrieval + Context + Generation


==================================================
2. WHY RAG IS NEEDED
==================================================

			LLMs are powerful, but they have limitations.

			Without RAG:

				User
				 ↓
				LLM
				 ↓
				Answer

			With RAG:

				User
				 ↓
				Retriever
				 ↓
				External Knowledge
				 ↓
				Relevant Context
				 ↓
				LLM
				 ↓
			       Answer


			Main reasons for using RAG:

				1. Private / Enterprise Data
				2. Frequently Changing Information
				3. Domain-Specific Knowledge
				4. Reduce Unsupported Answers
				5. Provide Evidence / Context
				6. Avoid Retraining the Model for Every Document Update


			Example:

				Company has internal documents:

				    Employee Policy
				    Financial Reports
				    Technical Manuals
				    Customer Documents
				    Insurance Claims

			The base LLM does not automatically have access to these documents.

			RAG allows the application to retrieve the required information and provide it to the LLM.


==================================================
3. LLM KNOWLEDGE LIMITATION
==================================================

		An LLM learns patterns and information during training.

		The model does not automatically know:

		    - Your private company documents
		    - Your internal database
		    - Newly uploaded documents
		    - Latest internal policies
		    - Customer-specific information
		    - Private financial records

		Example:

			Your company uploads:

			    Employee_Policy_2026.pdf

			User asks:

			    "What is our current work-from-home policy?"

			The base LLM does not automatically have access to this PDF.

			RAG solves this problem by retrieving the relevant information and putting it into the LLM context.


		Important:

			RAG does NOT mean that the LLM itself has learned the document permanently.

			Instead:

				Document
				   ↓
				Stored in Knowledge Base
				   ↓
				Retrieved at query time
				   ↓
				Provided to LLM as Context
				   ↓
				LLM generates Answer


==================================================
RAG VS FINE-TUNING
==================================================

		RAG:

			Documents
			    ↓
			Knowledge Base
			    ↓
			Retrieve Information
			    ↓
			Context
			    ↓
			LLM
			    ↓
			Answer


		Fine-Tuning:

			Training Data
			    ↓
			Fine-Tuning
			    ↓
			Updated Model Weights
			    ↓
			Model


		Important interview point:

			RAG changes the information supplied to the model at inference time.

			Fine-tuning changes the model's learned parameters/weights.


==================================================
4. EXTERNAL KNOWLEDGE RETRIEVAL
==================================================

		Retrieval is the "R" in RAG.

		The retrieval system searches external knowledge sources and finds information relevant to the user's question.


		Possible knowledge sources:

		    PDF
		    DOCX
		    TXT
		    Excel
		    CSV
		    Web Pages
		    Databases
		    APIs
		    Vector Databases
		    Knowledge Graphs
		    Internal Company Systems


		Example:

			Documents:

			    HR_Policy.pdf
			    Finance_Policy.pdf
			    Security_Policy.pdf

			Question:

			    "What is the password policy?"

			Retriever searches the knowledge base.

			It should find:

			    Security_Policy.pdf
				  ↓
			    Password Policy Section
				  ↓
		   	   Relevant Chunks


		   The system does NOT need to send the entire document collection to the LLM.

		   It retrieves only the most relevant information.

==================================================
6. RAG PIPELINE
==================================================

		RAG has two major pipelines:

			1. Indexing Pipeline
			2. Query Pipeline


--------------------------------------------------
A. INDEXING PIPELINE
--------------------------------------------------

		The indexing pipeline runs before the user asks questions.

		Flow:

			Documents
			    ↓
			Document Loading
			    ↓
			Text Extraction
			    ↓
			  OCR
			    ↓
			Text Cleaning
			    ↓
			Chunking
			    ↓
			Embedding Generation
			    ↓
			Vector Database


		Example:

			100-page PDF
			    ↓
			Extract Text
			    ↓
			100 pages of text
			    ↓
			Chunking
			    ↓
			1000 chunks
			    ↓
			Embedding Model
			    ↓
			1000 vectors
			    ↓
			Vector Database


		Example embedding:

			Chunk:

			    "Employees are eligible for 12 sick leaves per year."

			Embedding:

			    [0.12, -0.43, 0.78, 0.21, ...]


			Stored in Vector DB with metadata:

			{
			    "text": "Employees are eligible for 12 sick leaves per year.",
			    "file_name": "Leave_Policy.pdf",
			    "page_number": 5,
			    "section": "Sick Leave"
			}


--------------------------------------------------
B. QUERY PIPELINE
--------------------------------------------------

		This happens when the user asks a question.

		Flow:

			User Question
			      ↓
			Query Processing
			      ↓
			Query Embedding
			      ↓
			Vector Search
			      ↓
			Top-K Results
			      ↓
			Optional Reranking
			      ↓
			Relevant Context
			      ↓
			Prompt Construction
			      ↓
			   LLM
			      ↓
			Final Answer


		Example:

			User asks:

			    "How many sick leaves can I take?"


			Step 1:

				Convert question into an embedding.

				Question
				    ↓
				Embedding Model
				    ↓
				Query Vector


			Step 2:

				Search Vector Database.

				Query Vector
				    ↓
				Similarity Search
				    ↓
				Top-K Chunks


			Step 3:

				Optional reranking.

				Top 50 results
				      ↓
				Reranker
				      ↓
				Top 5 relevant results


			Step 4:

				Build LLM context.

				Context:

				    "Employees are eligible for 12 sick leaves per year."


				Question:

				    "How many sick leaves can I take?"


			Step 5:

				Send context + question to LLM.

				LLM
				 ↓
				Final Answer

==================================================
IMPORTANT RAG COMPONENTS
==================================================

		1. Document Loader
		   - Loads PDF, DOCX, TXT, Excel, etc.

		2. OCR
		   - Extracts text from scanned documents/images.

		3. Text Cleaning
		   - Removes unnecessary noise.

		4. Chunking
		   - Splits large documents into smaller meaningful pieces.

		5. Embedding Model
		   - Converts text into numerical vectors.

		6. Vector Database
		   - Stores and searches embeddings.

		   Examples:
		       ChromaDB
		       FAISS
		       Pinecone
		       Qdrant
		       Weaviate
		       Milvus

		7. Retriever
		   - Finds relevant chunks.

		8. Metadata Filter
		   - Filters documents based on metadata.

		9. Reranker
		   - Reorders retrieved results based on relevance.

		10. Context Builder
		    - Builds the information supplied to the LLM.

		11. LLM
		    - Generates the final answer.

		12. Evaluation
		    - Measures retrieval and generation quality.


==================================================
RAG RETRIEVAL METHODS
==================================================

			Dense Retrieval
			    ↓
			Uses embeddings and semantic similarity.


			Sparse Retrieval
			    ↓
			Uses keyword-based retrieval.

			Example:
			    BM25


			Hybrid Search
			    ↓
			Combines:

			    Dense Retrieval
				  +
			    Sparse Retrieval


			Example:

			User Query
			     |
			     +----------> Dense Search
			     |
			     +----------> BM25
			     |
			     v
			   Combine Results
			     |
			     v
			   Reranking
			     |
			     v
			 Final Context


==================================================
RAG WITH RERANKING
==================================================

		A production RAG system may retrieve many documents first and then rerank them.

		Example:

			User Query
			    ↓
			Vector DB
			    ↓
			Retrieve 50 chunks
			    ↓
			Reranker
			    ↓
			Select Top 5
			    ↓
			LLM
			    ↓
			Answer


		Why?

			Vector search may find semantically similar documents, but some results may not be highly relevant.

			Reranking improves the ordering of retrieved results.

RAG EVALUATION
==================================================

			A RAG system should be evaluated at multiple levels.


			RETRIEVAL METRICS:

			    Recall@K
			    Precision@K
			    MRR
			    NDCG
			    Hit Rate


			GENERATION METRICS:

			    Faithfulness
			    Answer Relevance
			    Context Relevance
			    Correctness


			SYSTEM METRICS:

			    Retrieval Latency
			    Generation Latency
			    Token Usage
			    Cost


			Important:

			Good RAG requires both:

			    Good Retrieval
				   +
			    Good Generation


			If retrieval is bad:

			    Bad Context
			       ↓
			    Bad Answer


			If retrieval is good:

			    Relevant Context
			       ↓
			    Better Grounded Answer

==================================================
INTERVIEW ANSWER
==================================================

Question:

	"What is RAG?"


	Answer:

		"RAG, or Retrieval-Augmented Generation, is an architecture that combines information retrieval with a Large Language Model. During indexing, documents are processed, chunked, converted into embeddings, and stored in a retrieval system such as a vector database. At query time, the user's question is converted into an embedding and used to retrieve relevant chunks. Those chunks are provided as context to the LLM, which generates a grounded response. RAG is particularly useful for private, domain-specific, or frequently changing information because the knowledge base can be updated without retraining the LLM."

==================================================
3. PDF PROCESSING
==================================================

			PDF processing is especially important in enterprise RAG because PDFs
			can contain different types of content.


			Types of PDFs:

				1. Text-based PDF

				    PDF contains selectable text.

				    Example:

				    Employee Leave Policy
				    Sick Leave: 12 days


				2. Scanned PDF

				    PDF contains scanned images instead of actual text.

				    Example:

				    Scanner
				       ↓
				    Image
				       ↓
				    PDF


				3. Mixed PDF

				    Some pages contain text.
				    Some pages contain images/scans.


				4. Complex PDF

				    PDF may contain:

				    Tables
				    Images
				    Headers
				    Footers
				    Multiple columns
				    Forms
				    Charts
				    Signatures


				PDF processing strategy:

						 PDF
						  ↓
					    Detect PDF Type
						  ↓
					+---------+---------+
					|                   |
				     Text PDF           Scanned PDF
					|                   |
				   Text Extraction          OCR
					|                   |
					+---------+---------+
						  ↓
					     Clean Text
						  ↓
					       Chunking


				Example:

					PDF
					 ↓
					Check extracted text
					 ↓
					If text exists → use text extraction
					 ↓
					If text is missing/poor → OCR
					 ↓
					Combine extracted content


					Useful tools:

					    PyMuPDF

					    RapidOCR

					 ↓

					 ↓

				Important PDF processing challenges:

				    1. Scanned pages

			OCR example:

			    Image
			        ↓
			    PaddleOCR
			        ↓
			    Detected Text
			        ↓
			    Structured Text


			Important extraction information to preserve:

			    Page Number
			    File Name
			    Section
			    Table Information
			    Coordinates when needed
			    Document Type
			    Document Version


			Example:

			{
			    "page_no": 5,
			    "text": "Employees are eligible for 12 sick leaves..."
			}


			Do not immediately remove important information such as:

			    Names
			    Email addresses
			    Phone numbers
			    URLs
			    Dates
			    Document IDs
			    Claim numbers
			    Invoice numbers
			    Policy numbers


			These may be important for retrieval and downstream extraction.


==================================================
5. CLEANING
==================================================

			Raw extracted text often contains noise.

			Example raw text:

			    Employee    Leave    Policy


			    Page 5


				    Employees are eligible for
				    12 sick leaves per year.


			  	    www.company.com


			 	    Cleaning converts noisy text into useful text.


			Typical cleaning operations:

			    1. Remove unnecessary whitespace
			    2. Normalize line breaks
			    3. Remove repeated headers
			    4. Remove repeated footers
			    5. Remove unnecessary page numbers
			    6. Normalize encoding
			    7. Remove OCR artifacts
			    8. Normalize special characters
			    9. Remove duplicate text
			    10. Preserve meaningful structure


		Example:

			Raw:

			    Employee     Leave       Policy


			    Page 5


			    Employees are eligible for
			    12 sick leaves per year.


			Cleaned:

			    Employee Leave Policy

			    Employees are eligible for 12 sick leaves per year.


			Important:

			Cleaning should NOT destroy useful information.

			Bad cleaning:

			    "Claim Number: CLM-2026-00123"

			becomes:

			    "Claim Number"


			This loses important information.

			Good cleaning:

			    "Claim Number: CLM-2026-00123"


		Preserve:

		    Names
		    Emails
		    Phone Numbers
		    URLs
		    Dates
		    IDs
		    Claim Numbers
		    Invoice Numbers
		    Amounts
		    Section Names


==================================================
6. CHUNKING
==================================================

		Chunking means splitting a large document into smaller pieces.

		Why?

			LLMs and embedding models cannot efficiently process unlimited amounts
			of text as one piece.

			Example:

			100-page PDF
			      ↓
			Large Text
			      ↓
			Chunking
			      ↓
			Chunk 1
			Chunk 2
			Chunk 3
			...
			Chunk 500


		Example:

			Original:

			    Employee Leave Policy

			    Employees are eligible for 12 sick leaves per year.
			    Employees must submit a leave request to their manager.
			    Emergency leave should be reported immediately.
			    ...


			After chunking:

			    Chunk 1:
			    Employee Leave Policy

			    Chunk 2:
			    Employees are eligible for 12 sick leaves per year.

			    Chunk 3:
			    Employees must submit a leave request to their manager.

			    Chunk 4:
			    Emergency leave should be reported immediately.


			The goal is:

			    Smaller searchable units
				  +
			    Enough context
				  +
			    Meaningful boundaries


==================================================
TYPES OF CHUNKING
==================================================

		1. Fixed-Size Chunking

		Example:

		    Every 500 characters/tokens.


		2. Recursive Character Chunking

			Splits using separators such as:

			    Paragraph
			    Sentence
			    Word
			    Character


			Typical order:

			    "\n\n"
			    "\n"
			    " "
			    ""


		3. Sentence-Based Chunking

			Split according to sentences.


		4. Paragraph-Based Chunking

			Split according to paragraphs.


		5. Semantic Chunking

			Split based on semantic similarity.


		6. Document Structure-Based Chunking

			Use:

			    Title
			    Section
			    Subsection
			    Paragraph
			    Table


		7. Markdown Chunking

			Use:

			    Headers
			    Sections
			    Lists
			    Code blocks


		8. Table-Aware Chunking

			Treat tables carefully so that row/column relationships are preserved.


==================================================
RECURSIVE CHUNKING
==================================================

			A common approach for RAG is recursive character splitting.

			Example:

				Text
				 ↓
				Try paragraph separator
				 ↓
				If chunk is still too large
				 ↓
				Try line separator
				 ↓
				If still too large
				 ↓
				Try word separator
				 ↓
				If still too large
				 ↓
				Split further


			Example:

			    from langchain_text_splitters import RecursiveCharacterTextSplitter

			    splitter = RecursiveCharacterTextSplitter(
				chunk_size=1000,
				chunk_overlap=200
			    )

			    chunks = splitter.split_text(text)


			Result:

			    Chunk 1
			    Chunk 2
			    Chunk 3
			    ...


==================================================
7. CHUNK SIZE
==================================================

Chunk size defines approximately how much text is placed into each
chunk.

Example:

    chunk_size = 500

means the splitter attempts to create chunks around that size,
depending on the splitting strategy and unit used.


Example:

Large Document
      ↓
500-token chunks


Possible sizes:

    200
    300
    500
    800
    1000
    1500
    2000


There is NO universal best chunk size.


Chunk size depends on:

    1. Document type
    2. Content structure
    3. Embedding model
    4. Retrieval method
    5. Query type
    6. LLM context window
    7. Reranker
    8. Expected answer size


Example:

Short FAQ:

    200-400 tokens


Technical documentation:

    400-800 tokens


Long policy documents:

    500-1000 tokens


Complex financial documents:

    300-800 tokens


These are starting points, NOT fixed rules.


Important:

Chunk size should be evaluated experimentally.


Too Small:

    Document
      ↓
    Tiny chunks
      ↓
    Missing context
      ↓
    Poor retrieval


Too Large:

    Document
      ↓
    Huge chunks
      ↓
    Too much unrelated information
      ↓
    Poor retrieval precision


Ideal:

    Meaningful Chunk
          ↓
    Enough Context
          ↓
    Good Retrieval
          ↓
    Better Answer


==================================================
CHUNK SIZE AND EMBEDDINGS
==================================================

Embedding model characteristics matter.

Examples:

    SentenceTransformers
    BGE
    E5
    OpenAI Embeddings
    Qwen embedding models


Do NOT choose chunk size only because an embedding model has a certain
maximum sequence length.

Instead consider:

    Document Structure
    Semantic Meaning
    Query Type
    Model Limits
    Retrieval Quality


Important distinction:

Embedding model
    ↓
Converts chunk → vector


LLM
    ↓
Uses retrieved chunks → answer


Therefore chunk size must work well for both retrieval and generation.


==================================================
8. CHUNK OVERLAP
==================================================

Chunk overlap means repeating some content between consecutive chunks.


Example:

Chunk Size = 500 tokens
Overlap = 100 tokens


Then:

Chunk 1:
    Tokens 1 - 500

Chunk 2:
    Tokens 401 - 900

Chunk 3:
    Tokens 801 - 1300


The overlapping section helps preserve context across chunk boundaries.


Without overlap:

    Chunk 1:
    "...employee must submit the request to the"


    Chunk 2:
    "manager before taking leave."


The meaning is split across chunks.


With overlap:

    Chunk 1:
    "...employee must submit the request to the manager"


    Chunk 2:
    "submit the request to the manager before taking leave."


The important relationship can remain available.


Typical starting values:

    Chunk Size = 500
    Chunk Overlap = 50-100


or:

    Chunk Size = 1000
    Chunk Overlap = 100-200


Again:

There is NO universal optimal overlap.


Too little overlap:

    Important context may be lost.


Too much overlap:

    Duplicate information
        ↓
    More chunks
        ↓
    More storage
        ↓
    More retrieval noise
        ↓
    Higher cost


A common starting range is:

    10% - 20% overlap


Then evaluate retrieval performance.


==================================================
CHUNK SIZE + OVERLAP EXAMPLE
==================================================

Suppose:

    Document = 10,000 tokens
    Chunk Size = 500
    Overlap = 100


Conceptually:

Chunk 1:
    1 - 500

Chunk 2:
    401 - 900

Chunk 3:
    801 - 1300

Chunk 4:
    1201 - 1700

...


Overlap:

    100 tokens


Step size:

    500 - 100 = 400 tokens


Approximate number of chunks:

    (10,000 - 100) / 400
    ≈ 24.75

So approximately 25 chunks.

Actual chunk count can differ because real splitters follow
text boundaries.

IMPORTANT DOCUMENT PROCESSING PRINCIPLES
==================================================

1. Preserve document structure whenever possible.

2. Preserve important identifiers.

3. Do not blindly remove numbers.

4. Do not remove names, emails, URLs, dates, IDs, or claim numbers
   if they are relevant to retrieval.

5. Use OCR for scanned documents.

6. Choose chunk boundaries based on meaning.

7. Start with a reasonable chunk size and evaluate.

8. Use overlap to preserve boundary context.

9. Avoid excessive overlap.

10. Store useful metadata.

11. Use metadata filtering for enterprise retrieval.

12. Track document versions.

13. Handle duplicate documents.

14. Support incremental updates.

15. Log extraction and processing errors.


==================================================
COMMON INTERVIEW QUESTIONS
==================================================

Q1. Why do we chunk documents?

Answer:

Large documents are split into smaller meaningful pieces so that
retrieval can identify relevant information more precisely and the
retrieved context can fit efficiently into the model's context window.


Q2. What happens if chunks are too small?

Answer:

Too-small chunks may lose contextual information and make it difficult
for the retriever or LLM to understand the complete meaning.


Q3. What happens if chunks are too large?

Answer:

Large chunks may contain unrelated information, reduce retrieval
precision, increase context size, and increase processing cost.


Q4. What is chunk overlap?

Answer:

Chunk overlap is the repeated content shared between consecutive chunks.
It helps preserve context when important information crosses a chunk
boundary.


Q5. Why do we need metadata?

Answer:

Metadata provides additional information about a chunk, such as file
name, page number, document type, section, and version. It supports
filtering, traceability, citations, debugging, and access control.


Q6. How do you process scanned PDFs?

Answer:

First determine whether the PDF contains usable text. If it is scanned,
render the pages as images and apply OCR using tools such as PaddleOCR,
RapidOCR, or Tesseract. Then clean and chunk the extracted text.


Q7. Is there a universal best chunk size?

Answer:

No. Chunk size depends on document structure, content type, embedding
model, retrieval strategy, query type, reranker, and LLM context
requirements. It should be selected experimentally and evaluated using
retrieval metrics and end-to-end answer quality.


Q8. Why not send the entire document to the LLM?

Answer:

Large documents may exceed context limits, increase latency and cost,
and introduce irrelevant information. Retrieval selects the most
relevant content before generation.

			User Query
			      ↓
			Query Processing
			      ↓
			Embedding Generation
			      ↓
			Vector Search
			      ↓
			Reranking
			      ↓
			Context Selection
			      ↓
			Prompt Construction

			Final Answer


==================================================
1. INPUT QUERY
==================================================

		Input Query is the question or request provided by the user.

		It is the starting point of the RAG query pipeline.

		Example:

			"How many sick leaves can an employee take?"

		Basic flow:

			User
			  ↓
			Question
			  ↓
			RAG Pipeline


		Examples:

			"What is the company's leave policy?"

			"Why was the insurance claim rejected?"

			"What is the invoice payment deadline?"

			"What are the BOL details?"

			"What is the refund policy?"


		The goal is to understand what information the user is
		requesting and retrieve the relevant information from the
		knowledge base.


==================================================
2. QUERY PROCESSING
==================================================

		Query Processing improves or transforms the original user
		query before retrieval.

		Query Processing can include:

			1. Query Rewrite
			2. Query Expansion
			3. Query Transformation


		Flow:

			Original Query
			      ↓
			Query Processing
			      ↓
			Improved / Transformed Query
			      ↓
			Embedding
			      ↓
			Retrieval


		Why Query Processing is needed:

			Users may provide:

				- Short queries
				- Ambiguous queries
				- Incomplete queries
				- Conversational questions
				- Misspelled queries
				- Domain-specific terminology


		Example:

			Original Query:

				"leave?"


			Processed Query:

				"What is the employee leave policy?"


		Query processing improves the chance of retrieving
		the correct information.


--------------------------------------------------
2.1 QUERY REWRITE
--------------------------------------------------

		Query Rewrite means changing the wording of the original
		query to make it clearer and more suitable for retrieval.

		The original meaning or intent should remain the same.


		Example:

			Original Query:

				"How much leave can I take?"


			Rewritten Query:

				"How many leave days is an employee entitled to?"


		Another example:

			Conversation:

				User:

				"What is the refund period?"


				User:

				"What about international orders?"


			The second query is incomplete.

			Query Rewrite can convert it to:

				"What is the refund period for international orders?"


		Flow:

			Original Query
			      ↓
			Query Rewriter
			      ↓
			Clear Query
			      ↓
			Retriever


		Benefits:

			- Resolves ambiguity
			- Adds missing conversational context
			- Improves search quality
			- Makes the query retrieval-friendly


		Important:

			Query Rewrite should preserve the user's original intent.


--------------------------------------------------
2.2 QUERY EXPANSION
--------------------------------------------------

		Query Expansion adds related terms, synonyms, or concepts
		to the original query.

		Example:

			Original Query:

				"sick leave"


			Expanded Query:

				"sick leave, medical leave, illness leave,
				 employee leave"


		Another example:

			Original Query:

				"BOL"


			Expanded Query:

				"BOL, Bill of Lading, shipping document,
				 freight document, carrier document"


		Why Query Expansion?

			The user and the document may use different terminology.


		Example:

			User Query:

				"sick leave"


			Document:

				"medical leave"


		Query expansion can help connect these related concepts.


		Flow:

			Original Query
			      ↓
			Query Expansion
			      ↓
			Related Terms
			      ↓
			Retrieval


		Types of Query Expansion:

			1. Synonym Expansion
			2. Keyword Expansion
			3. Semantic Expansion
			4. Domain-Specific Expansion
			5. LLM-Based Expansion


--------------------------------------------------
2.3 QUERY TRANSFORMATION
--------------------------------------------------

		Query Transformation converts the original query into
		one or more alternative queries or representations.


		Example:

			Original Query:

				"Why was my insurance claim rejected?"


			Transformed Queries:

				Query 1:
				"Insurance claim rejection reason"


				Query 2:
				"Claim denial reasons"


				Query 3:
				"Insurance claim eligibility conditions"


		The system can retrieve results for multiple queries and
		combine the results.


		Flow:

				Original Query
				      ↓
				Query Transformation
				      ↓
			  +-------+-------+-------+
			  ↓       ↓       ↓
			Query 1 Query 2 Query 3
			  ↓       ↓       ↓
			Retrieve Retrieve Retrieve
			  ↓       ↓       ↓
			  +-------+-------+-------+
				      ↓
				Combined Results
				      ↓
				    Reranking


		Benefits:

			- Improves retrieval coverage
			- Handles complex questions
			- Finds information using different terminology
			- Useful for ambiguous queries


==================================================
QUERY REWRITE vs QUERY EXPANSION vs QUERY TRANSFORMATION
==================================================

		QUERY REWRITE

			Purpose:

				Make the original question clearer.

			Example:

				"leave?"

				    ↓

				"What is the employee leave policy?"


		QUERY EXPANSION

			Purpose:

				Add related terms or concepts.

			Example:

				"sick leave"

				    ↓

				"sick leave, medical leave, illness leave"


		QUERY TRANSFORMATION

			Purpose:

				Create alternative queries or representations.

			Example:

				"Why was my claim rejected?"

				    ↓

				"claim rejection reason"
				"claim denial reason"
				"claim eligibility conditions"


		Easy Memory:

			Rewrite
			   ↓
			Improve the question


			Expansion
			   ↓
			Add related terms


			Transformation
			   ↓
			Create alternative search queries


==================================================
3. EMBEDDING GENERATION
==================================================

		Embedding Generation converts the processed query into
		a numerical vector.

		Example:

			Query:

				"How many sick leaves are allowed?"


			Embedding Model:

				SentenceTransformer
				OpenAI Embeddings
				BGE
				E5
				Qwen Embedding Model


			Output:

				[0.12, -0.43, 0.71, 0.25, ...]


		The vector represents the semantic meaning of the query.


		Flow:

			Query
			  ↓
			Embedding Model
			  ↓
			Query Vector


		Documents are also converted into vectors during the
		indexing phase.


			Document Chunk
			      ↓
			Embedding Model
			      ↓
			Document Vector


		At query time:

			User Query
			      ↓
			Query Embedding
			      ↓
			Query Vector
			      ↓
			Vector Database


		The query vector is compared with document vectors.


--------------------------------------------------
QUERY EMBEDDING vs DOCUMENT EMBEDDING
--------------------------------------------------

		INDEXING TIME:

			Document
			    ↓
			Chunking
			    ↓
			Embedding
			    ↓
			Document Vector
			    ↓
			Vector Database


		QUERY TIME:

			User Query
			    ↓
			Embedding
			    ↓
			Query Vector
			    ↓
			Vector Database


		The query and document representations should generally
		be compatible and belong to the same embedding space.


		Example:

			Document:

				"Employees are eligible for 12 sick leaves per year."


			Document Vector:

				[0.10, 0.43, -0.21, ...]


			Query:

				"How many sick leaves can I take?"


			Query Vector:

				[0.11, 0.41, -0.19, ...]


		Because the meanings are related, their vectors may be
		close in the embedding space.


==================================================
4. VECTOR SEARCH
==================================================

		Vector Search finds document chunks that are semantically
		similar to the query vector.


		Flow:

			Query
			  ↓
			Query Embedding
			  ↓
			Vector Database
			  ↓
			Similarity Search
			  ↓
			Top-K Results


		Example:

			Query:

				"How many sick leaves are allowed?"


			Vector Database contains:

				Chunk 1 → Salary Policy
				Chunk 2 → Sick Leave Policy
				Chunk 3 → Travel Policy
				Chunk 4 → Attendance Policy
				Chunk 5 → Insurance Policy


			Vector Search:

				Query
				  ↓
				Vector DB
				  ↓
				Top-K Similar Chunks


			Example Result:

				1. Chunk 2
				2. Chunk 4
				3. Chunk 1
				4. Chunk 5
				5. Chunk 3


		The retrieved chunks become candidate results for the
		next stage.


--------------------------------------------------
SIMILARITY SEARCH
--------------------------------------------------

		Common similarity/distance metrics:

			1. Cosine Similarity
			2. Dot Product
			3. Euclidean Distance


		Cosine Similarity:

			Measures the angle between two vectors.

			Query Vector
			      ↕
			Document Vector


			Higher cosine similarity generally indicates
			greater similarity.


		Dot Product:

			Calculates the dot product between vectors.

			Depending on the embedding model and normalization,
			higher scores can represent stronger similarity.


		Euclidean Distance:

			Measures the geometric distance between vectors.

			Smaller distance means the vectors are closer.


--------------------------------------------------
TOP-K RETRIEVAL
--------------------------------------------------

		K represents the number of candidate results retrieved.


		Example:

			K = 5


			Vector DB retrieves:

				Top 5 chunks


		Production example:

			User Query
			    ↓
			Vector Search
			    ↓
			Retrieve Top 50
			    ↓
			Reranking
			    ↓
			Select Top 5


		Why retrieve more initially?

			The first-stage retriever generally focuses on
			recall.

			The reranker can then identify the most relevant
			documents from the candidate set.


==================================================
5. RERANKING
==================================================

		Reranking means taking the initially retrieved documents
		and reordering them according to their relevance to the
		user's query.


		Flow:

			Query
			  ↓
			Vector Search
			  ↓
			Top 50
			  ↓
			Reranker
			  ↓
			Top 5
			  ↓
			Context Selection


		Example:

			Query:

				"Why was the insurance claim rejected?"


			Initial Retrieval:

				1. Claim Processing
				2. Claim Rejection
				3. Claim Submission
				4. Insurance Policy
				5. Customer Information


			Reranker examines the query and candidate documents
			more deeply and produces a better ordering.


		Common Reranking Approaches:

			Cross-Encoder
			BGE Reranker
			Cohere Rerank
			Jina Reranker
			LLM-Based Reranking


--------------------------------------------------
BI-ENCODER vs CROSS-ENCODER
--------------------------------------------------

		BI-ENCODER:

			Query
			  ↓
			Query Embedding

			Document
			  ↓
			Document Embedding

			Query Vector
			      ↓
			Similarity Search
			      ↓
			Candidate Documents


			Advantages:

				- Fast
				- Scalable
				- Suitable for first-stage retrieval
				- Works efficiently with large vector databases


		CROSS-ENCODER:

			Query + Document
			      ↓
			Cross-Encoder
			      ↓
			Relevance Score


			The Cross-Encoder directly evaluates the relationship
			between the query and document.


			Advantages:

				- More detailed query-document interaction
				- Often better ranking quality
				- Suitable for reranking a smaller candidate set


		Typical Architecture:

			Query
			  ↓
			Bi-Encoder
			  ↓
			Vector Search
			  ↓
			Top 50
			  ↓
			Cross-Encoder
			  ↓
			Top 5


==================================================
6. CONTEXT SELECTION
==================================================

		Context Selection decides which retrieved chunks should
		actually be sent to the LLM.


		Example:

			Vector Search
			     ↓
			 50 Chunks
			     ↓
			  Reranking
			     ↓
			 10 Chunks
			     ↓
		       Context Selection
			     ↓
			  5 Best Chunks
			     ↓
			   LLM


		Context Selection considers:

			1. Relevance
			2. Token Budget
			3. Diversity
			4. Duplicate Information
			5. Document Importance
			6. Metadata
			7. Query Requirements


		Goal:

			Maximum useful information
			          +
			Minimum unnecessary information


--------------------------------------------------
CONTEXT WINDOW
--------------------------------------------------

		An LLM has a finite context capacity.

		Sending too much irrelevant information can cause:

			- Higher token usage
			- Higher cost
			- Higher latency
			- More noise
			- Lower answer quality


		Example:

			Bad:

				50 Retrieved Chunks
				      ↓
				     LLM


			Better:

				50 Retrieved Chunks
				      ↓
				   Reranker
				      ↓
				  Top 5 Chunks
				      ↓
				     LLM


		The objective is to provide the LLM with high-quality,
		relevant context.


--------------------------------------------------
MMR - MAXIMUM MARGINAL RELEVANCE
--------------------------------------------------

		MMR can be used to improve diversity in retrieved results.

		MMR tries to select documents that are:

			Relevant to the query
			          +
			Different from already selected documents


		Without Diversity:

			Chunk 1 → Same information
			Chunk 2 → Same information
			Chunk 3 → Same information
			Chunk 4 → Same information


		With Diversity:

			Chunk 1 → Policy
			Chunk 2 → Exception
			Chunk 3 → Procedure
			Chunk 4 → Eligibility


		This can provide broader useful context.


--------------------------------------------------
CONTEXT COMPRESSION
--------------------------------------------------

		Context Compression removes unnecessary information from
		retrieved content before sending it to the LLM.


		Example:

			Retrieved Chunk
			      ↓
			  1000 Tokens
			      ↓
			 Compression
			      ↓
			   300 Tokens
			      ↓
			      LLM


		Benefits:

			- Less noise
			- Lower token usage
			- Lower cost
			- Better focus


==================================================
7. PROMPT CONSTRUCTION
==================================================

		Prompt Construction combines the information required
		by the LLM.


		A RAG prompt usually contains:

			1. System Instructions
			2. Retrieved Context
			3. User Question
			4. Output Instructions


		Example:

			SYSTEM:

				You are an enterprise document assistant.

				Answer using only the provided context.

				If the answer is not available in the context,
				say that the information was not found.


			CONTEXT:

				Employees are eligible for 12 sick leaves per year.

				Sick leave requests must be submitted through
				the HR portal.


			QUESTION:

				How many sick leaves can an employee take?


			OUTPUT INSTRUCTION:

				Give a concise answer and mention the source
				page when available.


		This complete structure becomes the prompt sent to the LLM.


--------------------------------------------------
GROUNDING
--------------------------------------------------

		Grounding means generating an answer based on retrieved
		evidence.


		Without RAG:

			User
			  ↓
			LLM
			  ↓
			Answer


		With RAG:

			User
			  ↓
			Retrieval
			  ↓
			Evidence
			  ↓
			LLM
			  ↓
			Grounded Answer


		Example:

			Context:

				"Employees are eligible for 12 sick leaves
				 per year."


			Question:

				"How many sick leaves can an employee take?"


			Grounded Answer:

				"Employees are eligible for 12 sick leaves
				 per year."


		Important:

			RAG can improve grounding, but it does NOT guarantee
			zero hallucinations.

			Hallucinations can still happen because of:

				- Incorrect retrieval
				- Missing information
				- Poor context
				- Incorrect prompt
				- LLM generation errors


==================================================
8. LLM RESPONSE GENERATION
==================================================

		The LLM receives:

			System Instructions
			          +
			Retrieved Context
			          +
			User Question


		Then generates the final response.


		Flow:

			Prompt
			  ↓
			LLM
			  ↓
			Generated Response
			  ↓
			Final Answer


		Example:

			Context:

				"Employees are eligible for 12 sick leaves
				 per year."


			Question:

				"How many sick leaves can an employee take?"


			LLM Response:

				"Employees are eligible for 12 sick leaves
				 per year."


		The LLM performs the generation.

		The Retriever performs the information retrieval.

==================================================
COMMON INTERVIEW QUESTIONS
==================================================

	Q1. What happens after the user enters a query?

		Answer:

			The query can be processed using rewriting,
			expansion, or transformation. It is then converted
			into an embedding and used to retrieve relevant
			documents. The retrieved candidates can be reranked,
			the best context selected, and the selected context
			plus the question is passed to the LLM.


	Q2. What is Query Rewrite?

		Answer:

			Query rewriting changes the wording of the original
			query to make it clearer and more suitable for
			retrieval while preserving the user's intent.


	Q3. What is Query Expansion?

		Answer:

			Query expansion adds related terms, synonyms, or
			domain-specific concepts to improve retrieval coverage.


	Q4. What is Query Transformation?

		Answer:

			Query transformation creates alternative queries or
			representations from the original query so that
			multiple retrieval paths can be used.


	Q5. Why use reranking after vector search?

		Answer:

			Vector search is efficient for retrieving a candidate
			set, but vector similarity may not perfectly represent
			detailed query-document relevance. A reranker examines
			the candidates more deeply and improves their ordering.


	Q6. Why retrieve 50 documents and send only 5 to the LLM?

		Answer:

			The first retrieval stage aims for high recall by
			creating a larger candidate set. Reranking then selects
			the most relevant documents. Sending fewer high-quality
			chunks reduces noise, token usage, latency, and cost.


	Q7. What is Context Selection?

		Answer:

			Context selection chooses the most useful retrieved
			information to send to the LLM while considering
			relevance, diversity, token budget, and query
			requirements.


	Q8. What is Prompt Construction?

		Answer:

			Prompt construction combines system instructions,
			retrieved context, the user's question, and
			application-specific instructions into the input
			sent to the LLM.


	Q9. Does RAG eliminate hallucination?

		Answer:

			No. RAG can improve grounding by supplying relevant
			evidence, but retrieval errors, missing information,
			poor context, and generation errors can still cause
			hallucinations.


	Q10. What is the difference between Retrieval and Generation?

		Answer:

			Retrieval finds relevant information from the knowledge
			base. Generation uses the retrieved information and
			user query to produce the final natural-language
			response.

# 4. RAG TYPES

		RAG can be implemented in different architectures depending on
		the complexity of the application, retrieval requirements,
		knowledge structure, and level of automation.

		The major RAG types are:

			1. Basic RAG
			2. Advanced RAG
			3. Modular RAG
			4. Hybrid RAG
			5. Graph RAG
			6. Agentic RAG
			7. Self RAG
			8. Corrective RAG (CRAG)


		Basic idea:

			Basic RAG
			    ↓
			Simple Retrieval
			    ↓
			LLM


			Advanced RAG
			    ↓
			Query Processing
			    ↓
			Retrieval
			    ↓
			Reranking
			    ↓
			LLM


			Hybrid RAG
			    ↓
			Dense Search + Sparse Search
			    ↓
			Combine Results
			    ↓
			Reranking
			    ↓
			LLM


			Graph RAG
			    ↓
			Knowledge Graph
			    ↓
			Entity / Relationship Retrieval
			    ↓
			LLM


			Agentic RAG
			    ↓
			Agent
			    ↓
			Planning
			    ↓
			Multiple Tools / Retrieval
			    ↓
			LLM


			Self-RAG
			    ↓
			Retrieve
			    ↓
			Generate
			    ↓
			Self-Evaluate
			    ↓
			Correct / Retrieve Again


			CRAG
			    ↓
			Retrieve
			    ↓
			Evaluate Retrieval Quality
			    ↓
			Correct Retrieval if Necessary
			    ↓
			Generate Answer


==================================================
1. BASIC RAG
==================================================

		Basic RAG is the simplest form of Retrieval-Augmented Generation.

		It uses a straightforward pipeline:

			User Query
			      ↓
			Query Embedding
			      ↓
			Vector Search
			      ↓
			Top-K Documents
			      ↓
			   LLM
			      ↓
			Answer


		Example:

			User:

				"What is the company's leave policy?"


			Flow:

				Query
				  ↓
				Embedding
				  ↓
				ChromaDB
				  ↓
				Top 5 Chunks
				  ↓
				LLM
				  ↓
				Answer


		Typical components:

			- Document Loader
			- Chunking
			- Embedding Model
			- Vector Database
			- Retriever
			- LLM


		Example technology stack:

			PDF
			  ↓
			RecursiveCharacterTextSplitter
			  ↓
			SentenceTransformer
			  ↓
			ChromaDB
			  ↓
			Qwen / Llama / GPT
			  ↓
			Answer


		Advantages:

			- Simple architecture
			- Easy to implement
			- Easy to understand
			- Low complexity
			- Good for small applications
			- Good for learning RAG fundamentals


		Limitations:

			- Basic retrieval
			- Limited query understanding
			- May retrieve irrelevant chunks
			- No advanced reranking
			- No self-correction
			- Limited handling of complex questions


		Best use cases:

			- Simple document Q&A
			- FAQ systems
			- Small knowledge bases
			- Prototype applications
			- Learning RAG


		Memory:

			Basic RAG =

				Query
				  ↓
				Retrieve
				  ↓
				LLM
				  ↓
				Answer

			- Query transformation
			- Metadata filtering
			- Hybrid retrieval
			- Reranking
			- MMR
			- Context compression
			- Query routing
			- Retrieval evaluation


		Example:

			User Query
			      ↓
			Query Rewrite
			      ↓
			Hybrid Retrieval

			Top 50

			Cross-Encoder Reranker

3. MODULAR RAG
==================================================

		Modular RAG organizes the RAG system into independent modules.

		Instead of building one fixed pipeline, individual components
		can be replaced, improved, or combined.


		Example modules:

			+---------------------+
			| Query Module       |
			+---------------------+

			+---------------------+
			| Retrieval Module   |
			+---------------------+

			+---------------------+
			| Reranking Module   |
			+---------------------+

			+---------------------+
			| Context Module     |
			+---------------------+

			+---------------------+
			| Generation Module  |
			+---------------------+


		Example:

			Query Module
			      ↓
			Retrieval Module
			      ↓
			Reranking Module
			      ↓
			Context Module
			      ↓
			Generation Module


		Each module can be changed independently.


		Example:

			Embedding Module:

				SentenceTransformer


			can later be replaced with:

				BGE Embedding


			without redesigning the entire RAG system.


		Another example:

			Vector Database:

				ChromaDB


			can be replaced with:

				Qdrant
				Pinecone
				Weaviate
				Milvus


		Advantages:

			- Flexible architecture
			- Easy maintenance
			- Easy testing
			- Easy replacement of components
			- Supports experimentation
			- Good for production systems


		Best use cases:

			- Large enterprise applications
			- Production RAG platforms
			- Systems requiring multiple retrieval strategies
			- Applications with frequently changing components


		Memory:

			Modular RAG =

				Independent RAG Components
				       ↓
				Can be replaced or combined


==================================================
4. HYBRID RAG
==================================================

		Hybrid RAG combines multiple retrieval strategies.

		The most common combination is:

			Dense Retrieval
			      +
			Sparse Retrieval


		Dense Retrieval uses embeddings.

		Sparse Retrieval uses keyword-based methods such as BM25.


		Architecture:

			User Query
			      ↓
			  +---+---+
			  |       |
			  ↓       ↓
			Dense   Sparse
			Search   Search
			  ↓       ↓
			Vector    BM25
			DB
			  ↓       ↓
			  +---+---+
			      ↓
			Combine Results
			      ↓
			Reranking
			      ↓
			Context
			      ↓
			LLM
			      ↓
			Answer


		Example:

			User Query:

				"Claim number CLM-2026-00123"


			Dense search may understand semantic meaning.

			Sparse search can strongly match the exact claim number.


		Hybrid search is useful because:

			Dense Search:

				Good for semantic meaning.


			Sparse Search:

				Good for exact keywords,
				names, IDs, numbers, codes, etc.


		Advantages:

			- Better retrieval coverage
			- Handles semantic queries
			- Handles exact keyword queries
			- Useful for enterprise documents
			- Strong for technical and financial data


		Best use cases:

			- Financial documents
			- Insurance claims
			- Legal documents
			- Product catalogs
			- Technical documentation
			- Enterprise search


		Memory:

			Hybrid RAG =

				Dense Search
				     +
				Sparse Search
				     ↓
				Combined Results
				     ↓
				Reranking
				     ↓
				LLM

		between entities and concepts.

		Traditional RAG:

			Query
			  ↓
			Vector Search
			  ↓
			Relevant Chunks


		Graph RAG:

			Query
			  ↓
			Entity Identification
			  ↓
			Knowledge Graph
			  ↓
			Entity + Relationship Retrieval
			  ↓
			Context
			  ↓
			LLM


		Example knowledge graph:

			Employee
			   |
			   | works_for
			   ↓
			Company
			   |
			   | has_policy
			   ↓
			Leave Policy
			   |
			   | allows
			   ↓
			12 Sick Leaves


		Another example:

			Customer
			    |
			    | owns
			    ↓
			Policy
			    |
			    | contains
			    ↓
			Claim
			    |
			    | rejected_due_to
			    ↓
			Policy Violation


		Graph RAG is useful when relationships between entities
		are important.


		Example question:

			"Which customers have claims associated with policies
			 that expired before the claim date?"


		This requires relationships between:

			Customer
			Claim
			Policy
			Policy Date
			Claim Date


		A knowledge graph can represent these relationships.


		Typical architecture:

			Documents
			      ↓
			Entity Extraction
			      ↓
			Relationship Extraction
			      ↓
			Knowledge Graph
			      ↓
			Graph Retrieval
			      ↓
			Context
			      ↓
			LLM


		Advantages:

			- Excellent for relationship-based questions
			- Good for multi-hop reasoning
			- Represents entities and relationships explicitly
			- Useful for complex enterprise knowledge


		Best use cases:

			- Knowledge management
			- Financial analysis
			- Research
			- Complex enterprise relationships
			- Multi-hop questions


		Memory:

			Graph RAG =

				Entities
				    +
				Relationships
				    ↓
				Knowledge Graph
				    ↓
				Retrieve Relationships
				    ↓
				LLM


==================================================
6. AGENTIC RAG
==================================================

		Agentic RAG uses an AI agent to decide:

			- What information to retrieve
			- Which tool to use
			- Whether another search is required
			- Whether the retrieved information is sufficient
			- What action should happen next


		Traditional RAG:

			Query
			  ↓
			Retrieve
			  ↓
			LLM
			  ↓
			Answer


		Agentic RAG:

			User Query
			      ↓
			    Agent
			      ↓
			Planning / Reasoning
			      ↓
			Choose Tool
			      ↓
			Retrieve / Search / API
			      ↓
			Analyze Result
			      ↓
			Need More Information?
			      ↓
			     YES
			      |
			      └───────────────→ Search Again
			      ↓
			     NO
			      ↓
			    Answer


		Example:

			User:

				"Compare the 2025 and 2026 insurance claim
				 rejection policies and tell me what changed."


		Agent may decide:

			Step 1:

				Search 2025 policy.


			Step 2:

				Search 2026 policy.


			Step 3:

				Compare both documents.


			Step 4:

				Identify changes.


			Step 5:

				Generate final answer.


		Agentic RAG can use tools such as:

			- Vector Database
			- Web Search
			- SQL Database
			- APIs
			- Calculator
			- Knowledge Graph
			- Document Search
			- Enterprise Applications


		Advantages:

			- Handles complex tasks
			- Multi-step retrieval
			- Dynamic tool selection
			- Can perform multiple searches
			- Can combine different data sources


		Limitations:

			- More complex
			- Higher latency
			- More expensive
			- Agent decisions can fail
			- Requires stronger monitoring and evaluation


		Best use cases:

			- Complex research
			- Enterprise assistants
			- Multi-document analysis
			- Multi-source question answering
			- Data analysis agents


		Memory:

			Agentic RAG =

				Query
				  ↓
				Agent
				  ↓
				Plan
				  ↓
				Choose Tool
				  ↓
				Retrieve
				  ↓
				Evaluate
				  ↓
				Retrieve Again if Needed
				  ↓
				Answer


==================================================
7. SELF-RAG
==================================================

		Self-RAG adds self-reflection and self-evaluation to the
		RAG process.

		The system evaluates whether it should retrieve information,
		whether the retrieved information is useful, and whether the
		generated answer is supported.


		Traditional RAG:

			Query
			  ↓
			Retrieve
			  ↓
			Generate
			  ↓
			Answer


		Self-RAG:

			Query
			  ↓
			Decide Whether to Retrieve
			  ↓
			Retrieve
			  ↓
			Generate
			  ↓
			Self-Evaluate
			  ↓
			Is Answer Supported?
			  ↓
			YES → Final Answer
			  ↓
			NO → Retrieve / Correct / Regenerate


		Example:

			User:

				"What is the latest policy for claim approval?"


			Self-RAG may:

				1. Decide retrieval is required.
				2. Retrieve policy documents.
				3. Generate an answer.
				4. Check whether the answer is supported.
				5. If unsupported, retrieve better information.
				6. Regenerate the answer.


		Self-RAG focuses on:

			- Retrieval decisions
			- Relevance
			- Support
			- Quality of generated answers


		Advantages:

			- Better answer quality
			- Better grounding
			- Can identify unsupported answers
			- Can perform additional retrieval when needed


		Limitations:

			- More computationally expensive
			- More complex
			- Requires evaluation logic
			- Can increase latency


		Best use cases:

			- High-quality Q&A
			- Research systems
			- Enterprise knowledge systems
			- Applications where answer correctness is important


		Memory:

			Self-RAG =

				Retrieve
				   ↓
				Generate
				   ↓
				Self-Check
				   ↓
				Correct if Necessary


==================================================
8. CORRECTIVE RAG (CRAG)
==================================================

		CRAG stands for Corrective Retrieval-Augmented Generation.

		CRAG adds a retrieval evaluation and correction step.

		The system checks the quality of retrieved documents before
		generating the final answer.


		Basic RAG:

			Query
			  ↓
			Retrieve
			  ↓
			LLM
			  ↓
			Answer


		CRAG:

			Query
			  ↓
			Retrieve
			  ↓
			Evaluate Retrieval Quality
			  ↓
			+-----------------------+
			|                       |
			| Relevant?             |
			|                       |
			+----------+------------+
			           |
		       +-------+-------+
		       |               |
		      YES              NO
		       |               |
		       ↓               ↓
		    Use Results    Correct Retrieval
		       |               |
		       |       +-------+-------+
		       |       |               |
		       |       ↓               ↓
		       |    Reformulate     External
		       |      Query          Search
		       |       |               |
		       |       +-------+-------+
		       |               |
		       +-------+-------+
			       ↓
			    Context
			       ↓
			      LLM
			       ↓
			    Answer


		Example:

			User:

				"What are the latest regulations for
				 insurance claims?"


			Step 1:

				Retrieve internal documents.


			Step 2:

				Evaluate retrieved information.


			Step 3:

				If the results are poor or outdated:

					- Reformulate the query
					- Retrieve again
					- Use another knowledge source
					- Potentially perform web search


			Step 4:

				Use corrected context.


			Step 5:

				Generate final answer.


		Advantages:

			- Detects poor retrieval
			- Can correct retrieval failures
			- Improves robustness
			- Useful when retrieval quality varies


		Limitations:

			- More complex than basic RAG
			- Additional processing
			- Higher latency
			- Requires retrieval evaluation


		Best use cases:

			- Enterprise search
			- Dynamic knowledge
			- High-quality document Q&A
			- Systems where retrieval failures are common


		Memory:

			CRAG =

				Retrieve
				   ↓
				Evaluate
				   ↓
				Good?
				↙   ↘
			  YES    NO
			   ↓      ↓
			 Use    Correct
			   \      /
			    \    /
			     ↓  ↓
			    LLM
			     ↓
			   Answer

==================================================
INTERVIEW QUESTIONS
==================================================

	Q1. What is Basic RAG?

		Answer:

			Basic RAG retrieves relevant documents using a simple
			retrieval mechanism and provides them to an LLM for
			answer generation.


	Q2. What is Advanced RAG?

		Answer:

			Advanced RAG improves the basic pipeline using
			techniques such as query rewriting, hybrid retrieval,
			metadata filtering, reranking, MMR, and context
			compression.


	Q3. What is Modular RAG?

		Answer:

			Modular RAG organizes the system into independent
			modules that can be replaced, optimized, or combined
			independently.


	Q4. What is Hybrid RAG?

		Answer:

			Hybrid RAG combines multiple retrieval methods,
			commonly dense vector retrieval and sparse keyword
			retrieval such as BM25.


	Q5. What is Graph RAG?

		Answer:

			Graph RAG uses entities and relationships represented
			in a knowledge graph to retrieve structured context,
			especially for relationship-heavy and multi-hop
			questions.


	Q6. What is Agentic RAG?

		Answer:

			Agentic RAG uses an AI agent to plan retrieval,
			select tools, perform multiple searches, evaluate
			results, and determine the next action dynamically.


	Q7. What is Self-RAG?

		Answer:

			Self-RAG adds self-reflection to the retrieval and
			generation process. The system evaluates whether
			retrieval is needed and whether the generated answer
			is sufficiently supported.


	Q8. What is CRAG?

		Answer:

			Corrective RAG evaluates the quality of retrieved
			information and performs corrective retrieval or
			query reformulation when the initial retrieval is
			poor.


	Q9. Can these RAG types be combined?

		Answer:

			Yes. These approaches are not necessarily mutually
			exclusive. A production system can combine hybrid
			retrieval, reranking, graph retrieval, agents,
			self-evaluation, and corrective retrieval.
